PERSISTENT STREAMING POPULAR-ITEMS PIPELINE (spec 005)

The popular-items analytics runs inside the Analytics Service as ONE persistent
pipeline for the life of the service, with 5 filters connected by queues:

1. TailIngest (reads the shared database)
   -> WindowFilter (slides the 1000-scan window by scan id, every 500)
   -> AggregationFilter (running per-SKU counts, updated incrementally)
   -> RankingFilter (top 200 by count, ties by SKU)
   -> OutputFilter (persists each window to the DB; latest-wins)

There is no per-slide pipeline run and no in-process trigger from the scan route.
The pipeline learns about scans only by tailing transaction_item, which the
Checkout Service writes; Checkout never calls Analytics.

FILTER DESCRIPTIONS:

TailIngest:
  Purpose: Follow the scan record as rows commit.
  Input:   SELECT id, sku FROM transaction_item WHERE id > last_id ORDER BY id LIMIT 1000
  Output:  ScanData(scan_id, sku) in id order, and Watermark(b) once every id <= b
           (b a multiple of 500) has arrived or been declared a gap.
  Notes:   Keeps a contiguous watermark so out-of-order commits are never skipped;
           a hole open longer than 1 s is a never-committed id and is skipped
           ("gap skipped id=N"). Sleeps 100 ms only when caught up or stuck.

WindowFilter:
  Purpose: Maintain the window by scan id.
  Input:   ScanData and Watermark items.
  Output:  Slide(window_start, window_end, added SKUs, evicted SKUs) per watermark.

AggregationFilter:
  Purpose: Keep per-SKU counts for the current window.
  Input:   Slide.
  Output:  WindowCounts(window_start, window_end, counts).
  Notes:   One Counter for the pipeline's lifetime: +added, -evicted per slide.

RankingFilter:
  Purpose: Rank the window.
  Input:   WindowCounts.
  Output:  RankedData with the top 200, ordered by (-count, sku).

OutputFilter:
  Purpose: Publish each window.
  Input:   RankedData via a one-item latest-wins slot.
  Output:  Upsert of popular_window_snapshot + commit per window
           ("window published start=S end=E").

COMMUNICATION MODEL:

  TailIngest --[q1, 10000]--> WindowFilter --[q2, 64]--> AggregationFilter
             --[q3, 64]--> RankingFilter --[latest-wins slot]--> OutputFilter

Bounded queues back-pressure the tail instead of growing memory; only the final
slot ever drops anything, and what it drops is a superseded window, never a scan.

LIFECYCLE:

A supervisor holds a PostgreSQL advisory lock (one pipeline across all Analytics
replicas), bootstraps from the latest 500-boundary minus 1000 so the first
window published is complete, rebuilds the pipeline from the database after any
error, and on shutdown stops the tail and lets TERMINATE drain downstream.
